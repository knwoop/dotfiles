# API Implementation Task Split Skill

Split API implementation into PR units based on your project's architecture.

## Usage

```
User: Split this API implementation into tasks
User: How should I break this into PRs?
User: [Design Doc] I want to implement this
```

---

## Step 1: Understand the Project's Layer Structure

Before splitting tasks, understand the project's architecture.

### What to Check

1. **CLAUDE.md / README / Docs** - Architecture description
2. **Directory structure** - `internal/`, `pkg/`, `src/`, etc.
3. **Existing similar implementations** - How similar APIs are implemented

### Information to Extract

| Item | Examples |
|------|----------|
| Layer names | Handler, Resolver, Service, Repository, Model, Loader, etc. |
| Layer paths | `internal/handler/`, `internal/service/`, etc. |
| Dependency direction | Handler → Service → Repository → Model |
| API definition location | `schema.graphql`, `proto/`, `openapi.yaml`, etc. |
| DB definition location | `migrations/`, `etc/schema/`, etc. |
| Code generation | xo, sqlc, gqlgen, protoc, etc. |

---

## Step 2: Split from Domain Outward

**Domain First** — Implement from the inside (business logic) to the outside (infrastructure/API).

### Splitting Principle

```
1 PR = 1 Layer (or 1 responsibility)

Implementation order: Domain → Usecase → Infrastructure/API
                      (inside)              (outside)
```

### Common Mapping Examples

**Clean Architecture**:
```
PR1: Domain (Entity, Value Object, Repository Interface)
PR2: Usecase / Application Service
PR3: DB definition (migration)
PR4: Repository implementation
PR5: API definition (Proto/GraphQL/OpenAPI)
PR6: Handler / Controller
```

**GraphQL + Loader**:
```
PR1: Service (business logic)
PR2: DB definition (migration)
PR3: Loader
PR4: GraphQL Schema
PR5: Resolver
```

**Simple MVC**:
```
PR1: Model (business logic)
PR2: DB definition
PR3: Controller + View
```

### Why Start from Domain

- Business logic won't be influenced by technical details (DB/API format)
- Domain layer has no dependencies, so it can be implemented and tested first
- Define Repository Interface first → implement later

### What Can Be Skipped

| Case | Skip |
|------|------|
| No DB changes | migration |
| Auto-generated Model | Model PR |
| Existing Service/Loader is sufficient | that layer |
| Extending existing API | API definition (if changes are small) |

## Basic Rules

### Implementation and Tests in the Same PR

```
❌ PR1: Service implementation
   PR2: Service tests

✅ PR1: Service implementation + tests
```

### Order from Domain to Outside

Implement from inside (domain) to outside (infrastructure/API):

```
Domain → Usecase/Service → Repository impl/Loader → Handler/Resolver
(inside)                                            (outside)
   ↑
 Start here
```

- Domain has no dependencies, so it can be implemented first
- Repository: define Interface first, implement after DB definition
- Handler/Resolver comes last (connect when everything is ready)

### Don't Modify Auto-generated Code

Code generated by xo, sqlc, gqlgen, etc. is managed separately.
Only include running the generation command in tasks.
